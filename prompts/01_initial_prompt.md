# Prompt 01 — Initial project prompt (Phase 0)

- **Date:** 2026-11-06
- **Phase:** 0
- **Goal:** Define the LLM's role, the project requirements and the phased workflow, and have the LLM ask clarifying questions before it recommends anything.

## Exact prompt text

```text
# Role
You are an expert engineer in aerial robotics, multirotor control, and simulation with NVIDIA Isaac Sim. You will help me develop a complete university project, with clean, well-commented, and reproducible code.

# Project context
I need to build a university project in which ALL the code for moving an aerial drone is generated by an LLM (you). Mandatory requirements:
1. Reference simulator: NVIDIA Isaac Sim.
2. The drone must take off, reach a predefined goal point (and optionally a sequence of waypoints), avoid obstacles of various kinds, and land.
3. The entire project will be published on GitHub, including ALL the prompts given to the LLM, in chronological order.

# Development environment (to be recommended by you)
I don't have a defined environment yet: I want you to recommend one. In Phase 0, propose the most suitable setup for the project, justifying each choice:
- Isaac Sim version to use (the most stable one and compatible with the drone extensions/libraries you will propose), and installation method (pip, workstation, or container).
- Recommended operating system and why.
- Minimum and recommended hardware requirements (GPU, VRAM, RAM, CPU, disk space), with alternatives if my PC is not sufficient (e.g., cloud instances with NVIDIA GPUs).
- Python version, environment manager (conda/venv), and main dependencies.
- Supporting tools: IDE, Git, and ROS 2 / PX4 if needed.
If you are not certain about a compatibility detail between versions, say so explicitly and tell me where to verify it in the official NVIDIA documentation.
Before making recommendations, ask me what hardware I have available, my experience level in Python/robotics, and how much time I have for the project.

# Functional requirements
The drone (quadcopter) must be able to:
- Arm, take off to a configurable altitude, and hover stably.
- Navigate from a start position to a goal point (x, y, z) defined in a configuration file.
- Follow a mission made of multiple waypoints.
- Avoid obstacles of various kinds:
  - simple static obstacles (cubes, cylinders, walls);
  - complex static obstacles (narrow corridors, suspended obstacles, "forests" of poles, U-shaped configurations that create local minima);
  - dynamic obstacles (moving obstacles with known or random trajectories).
- Perceive obstacles using simulated sensors (e.g., Isaac Sim LiDAR and/or depth camera), not by reading positions directly from the scene — except for a "ground truth" mode for debugging.
- Handle abnormal situations: unreachable goal, sudden obstacle, speed/altitude limits (geofence), emergency landing, return to home.
- Land in a controlled way at the goal point or at the start point.

# Architectural requirements
Propose a modular architecture, separating at least:
- Scene/environment: procedural generation of the various obstacle scenarios from YAML files.
- Drone model and simulator interface.
- State estimation (position, velocity, attitude).
- Low-level control (e.g., cascaded position → velocity → attitude PID control, or an equivalent justified approach).
- Global planning (e.g., A* / RRT* on a 3D occupancy map).
- Local and reactive obstacle avoidance (e.g., artificial potential fields, VFH, velocity obstacles), with handling of local minima.
- Mission state machine (IDLE → TAKEOFF → NAVIGATE → AVOID → LAND → EMERGENCY …).
- Logging, metrics, and visualization.

Before writing any code, briefly evaluate and compare these integration options, recommending the most suitable one consistent with the environment you propose and with my experience level:
(a) Pegasus Simulator (multirotor extension for Isaac Sim, optionally with PX4/ArduPilot);
(b) Isaac Lab (which includes a quadcopter example);
(c) Isaac Sim Python API with a drone model and direct force/thrust application written from scratch.
For each, list pros, cons, version compatibility, and dependencies. If you are unsure about a compatibility detail or an API, state it explicitly instead of making it up, and tell me where to verify it in the official documentation.

# GitHub repository structure
Propose and follow a structure similar to:
- README.md — description, requirements, installation, how to run each scenario, results, GIFs/screenshots.
- prompts/ — all prompts given to the LLM, numbered (01_initial_prompt.md, 02_..., etc.), each including: date, goal, exact prompt text, short summary of the response, and files generated/modified.
- src/ — code split into modules.
- config/ — drone, controller, and scenario parameters in YAML.
- scenarios/ — test scenario definitions.
- tests/ — unit tests for planners, controllers, and avoidance logic (runnable without Isaac Sim where possible).
- docs/ — architecture, design choices, diagrams, known limitations.
- results/ — logs, trajectory plots, metrics.
- requirements.txt / environment.yml, .gitignore, LICENSE.

# Validation and metrics
Define at least 5 test scenarios of increasing difficulty and, for each one, measure: success/failure, time to goal, path length, minimum distance to obstacles, number of collisions, final positioning error. Generate 3D trajectory plots and a summary table.

# Workflow (important)
- We work in PHASES. Do not generate everything at once.
- Phase 0: ask me the necessary clarifying questions, then propose the development environment, architecture, integration choice, phase plan, and repository structure. Wait for my confirmation.
- For each following phase: write complete, working code (no "..." or omitted parts), explain what it does, tell me how to run it and how to verify it, and list common errors.
- At the end of each phase, give me:
  1. the content of the prompts/NN_*.md file to save for that phase;
  2. the suggested Git commit message;
  3. the recommended prompt for the next phase.
- When I report errors or logs, analyze them and fix the code, clearly indicating the changes.
- Code in Python, PEP 8 compliant, with type hints and docstrings. All comments and documentation in English.

Start with Phase 0.
```
